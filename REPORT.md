## 1. Резюме (Executive Summary)
Для микросервиса «Расчет корзины и скидок» системы лояльности
выбрана СУБД, настроен репозиторий с защитой базовой линии,
автоматическая проверка качества кода (flake8 и GitHub Actions),
проанализирован legacy-алгоритм расчёта стоимости корзины и
подготовлен план ревью. Цель работы: снизить риск внесения
дефектов с самого начала разработки.

## 2. Сравнительный анализ технологий

### 2.1. Матрица принятия решений
| Критерий | Вес | PostgreSQL | MongoDB |
|---|---|---|---|
| Поддержка ACID-транзакций | 0.35 | 5 | 4 |
| Производительность чтения | 0.20 | 4 | 5 |
| Гибкость схемы данных | 0.15 | 3 | 5 |
| Стоимость владения (TCO) | 0.15 | 5 | 4 |
| Экосистема и специалисты | 0.15 | 5 | 4 |
| **Сумма весов** | **1.00** | | |

### 2.2. Расчет и обоснование выбора
Формула: `S_i = Σ (W_j × X_ij)`

- PostgreSQL = 0.35·5 + 0.20·4 + 0.15·3 + 0.15·5 + 0.15·5
  = 1.75 + 0.80 + 0.45 + 0.75 + 0.75 = **4.50**
- MongoDB = 0.35·4 + 0.20·5 + 0.15·5 + 0.15·4 + 0.15·4
  = 1.40 + 1.00 + 0.75 + 0.60 + 0.60 = **4.35**

Победитель: **PostgreSQL**. Для транзакций и баллов критична
целостность данных, поэтому вес ACID максимальный. Недостаток
гибкости схемы частично компенсируется типом JSONB.

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма
![UML Diagram](https://github.com/USER/REPO/blob/feature/review-plan/docs/uml_diagram.png?raw=true)

Выявленные «запахи кода»:
- Магические числа: 15000, 0.85, 500, 0.90, 0.97, 0.93, 0.70.
- Строковые литералы "SUMMER", "VIP" и числа 1 и 2 для уровня
  лояльности прямо в коде.
- Нет валидации входных данных (отрицательная сумма, None,
  некорректные `promos` и `tier`).
- Результат зависит от порядка промокодов, один промокод можно
  применить многократно (риск фрода).
- Неизвестные промокоды молча игнорируются.
- Денежные расчёты во float (ошибки округления).
- Одна функция делает всё сразу, нет docstring и аннотаций типов.
- Цепочки if/elif плохо расширяются: новый промокод требует
  правки кода.
- Неинформативные имена (`p`), нет тестов.

### 5.2. План code-review
Подход: асинхронное ревью через Pull Request по чек-листу,
с ролями автора, рецензента, модератора и секретаря.

Открытый Pull Request с `docs/review-plan.md`:
(https://github.com/Metad0ns/lab1-comprehensive-Kharitonov/pull/3)

Ключевые измеримые критерии: отсутствие магических чисел,
валидация входных данных, покрытие тестами > 80%, flake8
без замечаний.

Эскалация: автор и рецензент → Tech Lead → обсуждение
командой, решение фиксируется в PR.

## 6. Заключение
Защита ветки develop и обязательные Pull Request исключают
прямые изменения базовой линии. CODEOWNERS гарантирует, что код
проверяет назначенный владелец. CI с flake8 автоматически отсекает
формальные нарушения ещё до ревью, а план ревью с измеримыми
критериями направляет усилия людей на логику и риски. Вместе эти
меры снижают вероятность попадания дефектов в develop.
